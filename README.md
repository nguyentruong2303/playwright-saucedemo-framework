# Playwright SauceDemo Automation Framework

Automation testing framework for [SauceDemo](https://www.saucedemo.com/) using **Playwright**, **Cucumber (BDD)** via `playwright-bdd`, and the **Page Object Model** pattern.

## Tech Stack

- [Playwright](https://playwright.dev/) — browser automation & test runner
- [playwright-bdd](https://github.com/vitalets/playwright-bdd) — Gherkin/Cucumber support on top of native Playwright Test
- [Cucumber](https://cucumber.io/) — behavior-driven scenario syntax
- TypeScript
- GitHub Actions — CI/CD

## Project Structure

```
├── features/               # Gherkin feature files (business scenarios)
│   ├── login.feature
│   ├── menu.feature
│   ├── cart.feature
│   └── checkout-step-two.feature
├── steps/                  # Step definitions — bridge between Gherkin and Playwright
│   ├── login.steps.ts
│   ├── menu.steps.ts
│   ├── products.steps.ts
│   └── checkout-step-two.steps.ts
├── pages/                  # Page Object Model — reusable page interactions
│   ├── LoginPage.ts
│   ├── ProductsPage.ts
│   ├── CartPage.ts
│   ├── CheckoutStepOnePage.ts
│   ├── CheckoutStepTwoPage.ts
│   └── SideBarMenuPage.ts
├── .features-gen/           # Auto-generated by bddgen — not committed
├── playwright.config.ts
└── package.json
```

## Test Coverage

- **Login**: successful login, validation errors (empty fields), invalid credentials, locked-out user
- **Side bar menu**: navigation to All Items / About, Logout, Reset App State
- **Cart**: add/remove products, cart retains items after cancelling checkout
- **Checkout**: fill customer information (Data Table), verify item list and price summary (item total, tax, total)

## Prerequisites

- Node.js 20+
- npm

## Setup

```bash
git clone <repo-url>
cd playwright-saucedemo-framework
npm ci
npx playwright install --with-deps
```

## Running Tests

Generate test files from `.feature` files, then run:

```bash
npm test
```

Equivalent to:
```bash
npx bddgen && npx playwright test
```

### Other useful commands

| Command | Purpose |
|---|---|
| `npx bddgen --watch` | Auto-regenerate tests on `.feature` file changes |
| `npx playwright test --headed` | Run with visible browser |
| `npx playwright test --ui` | Run in interactive UI Mode |
| `npx playwright test --grep "@menu"` | Run tests matching a tag/name |
| `npx playwright show-report` | Open the last HTML report |

## Reports

After a run, an HTML report is generated with screenshots on failure and traces for failed/retried tests:

```bash
npx playwright show-report
```

## CI/CD

Tests run automatically via **GitHub Actions** (`.github/workflows/`) on every push and pull request, generating features via `bddgen` before executing the suite headlessly.

## Notes

## Challenges & Lessons Learned

Building this framework surfaced several real issues worth documenting — both for future reference and to show the debugging process behind the final result.

### 1. Cucumber Expression mismatches between `.feature` and step definitions

**Problem:** Step definitions failed with `Found step definitions with incorrect arguments` or `Missing step definitions`, even though the logic looked correct.

**Root cause:** Cucumber only treats `{...}` placeholders (e.g. `{string}`, `{int}`) as dynamic parameters. Literal quotes typed directly in a pattern (`"error message"`) are matched as fixed text, not captured as arguments — and any wording difference between the `.feature` sentence and the step definition pattern (even a synonym) causes a silent no-match.

**Fix / takeaway:** Always use `{string}` for dynamic values, never hardcode quotes in the pattern. Keep step wording consistent — pick one language (English or Vietnamese) for all feature files and enforce it project-wide to avoid mismatches like `I enter` vs `tôi đăng nhập với`.

### 2. Data Table key mismatches (`rowsHash()` / `hashes()`)

**Problem:** `toEqual()` assertions failed even when values looked identical — e.g. expected `{ tax: '$3.20' }`, received `{ 'tax Price': '$3.20' }`.

**Root cause:** `dataTable.rowsHash()` and `hashes()` use the exact header text from the `.feature` table as object keys. TypeScript doesn't type-check these dynamic keys, so a mismatch (`postalCode` vs `Postal Code`) only surfaces at runtime.

**Fix / takeaway:** Keep Data Table headers and TypeScript property names in the same naming convention (camelCase) project-wide. Define a shared `interface` for expected/actual shapes where possible to at least get editor-level warnings.

### 3. Playwright strict mode violation when looping over elements

**Problem:** `locator.textContent()` threw `strict mode violation: resolved to 2 elements` when trying to read the name/price/quantity of each cart item in a loop.

**Root cause:** Calling `this.page.locator(...)` inside a loop searches the *entire page* every time, not just the current item — `.nth(i)` alone doesn't scope subsequent locator calls unless they're chained from it.

**Fix / takeaway:** Always call `.locator()` on the scoped element (`item.locator(...)`), never on `this.page`, once inside a `.nth(i)` loop.

### 4. CI failure: `Cannot find module 'playwright-bdd'`

**Problem:** Tests ran fine locally but failed on GitHub Actions with a missing module error.

**Root cause:** The package was present in local `node_modules` but not properly saved to `package.json`/`package-lock.json`, so `npm ci` on CI didn't install it.

**Fix / takeaway:** Always verify `git status` / `package.json` after installing a new dependency, and ensure the CI workflow runs `bddgen` (to generate specs from features) *before* `playwright test`, in that order.

### 5. Duplicated test coverage between `.spec.ts` and `.feature`

**Problem:** After migrating a module to BDD, the original hand-written `.spec.ts` test still existed, covering the same scenarios twice.

**Takeaway:** Not everything belongs in Gherkin. User-facing behavior (login flows, error messages, cart state) fits BDD well; technical/implementation details (input field types, visual regression, performance) are better kept as plain Playwright `.spec.ts` tests. Decide per-case which layer owns each test, and remove duplicates once a scenario is fully migrated.

### 6. Context/token management when pairing with an AI assistant

**Takeaway:** Long AI-assisted sessions degrade in quality well before hitting the context limit. Proactively checking usage and compacting after completing each module (rather than after the whole session) kept guidance accurate and relevant throughout the project.
